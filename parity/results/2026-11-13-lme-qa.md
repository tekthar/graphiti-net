# Question answering on LongMemEval: graphiti-net against Python Graphiti

Date: 2026-11-13. Upstream: Graphiti v0.31.2 on Neo4j 5.26. graphiti-net: commit `7b41076`, in memory and on
PostgreSQL 16 with pgvector.

## Method

`parity/python/lme_qa.py` and `tools/GraphitiNet.Eval qa` (see [parity/README.md](../README.md)):

- **Questions:** 24 from `longmemeval_oracle.json` (shipped with upstream), 4 for each of the 6 question types, chosen
  with a fixed seed among the questions with the fewest messages
  ([2026-11-12-lme-qa-questions.json](2026-11-12-lme-qa-questions.json)). 316 messages per run.
- **Ingestion:** each question's haystack sessions, message by message, with `add_episode` / `AddEpisodeAsync`, as
  upstream's `eval_e2e_graph_building.py`; one group per question.
- **Retrieval:** `COMBINED_HYBRID_SEARCH_RRF`, facts and entities, 20 of each; context built as upstream's
  `search_results_to_context_string`.
- **Answering:** upstream's `eval.qa_prompt` with the question and the date it was asked. The grader checked that
  every answering prompt was identical, character for character, to the one upstream's `qa_prompt` builds from the
  stored context: 0 mismatches in 96 answers.
- **Grading:** upstream's `eval.eval_prompt` with `gpt-5.5` as judge, the same Python grader for every run.
- **Models:** `gpt-5-mini` for building and answering, `text-embedding-3-small` at 1,024 dimensions.

## Results

| Run | Correct | Single-session user | Single-session assistant | Preference | Multi-session | Knowledge update | Temporal |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Python Graphiti, run 1 | 18 / 24 | 4/4 | 2/4 | 3/4 | 3/4 | 3/4 | 3/4 |
| Python Graphiti, run 2 (control) | 19 / 24 | 4/4 | 2/4 | 4/4 | 2/4 | 3/4 | 4/4 |
| **graphiti-net, in memory** | **21 / 24** | 4/4 | 3/4 | 4/4 | 2/4 | 4/4 | 4/4 |
| **graphiti-net, PostgreSQL** | **21 / 24** | 4/4 | 2/4 | 4/4 | 3/4 | 4/4 | 4/4 |

| Run | Ingestion input / output tokens | Facts / entities | Median search |
| --- | --- | --- | --- |
| Python Graphiti, run 1 | 5,509,864 / 300,055 | 449 / 441 | 402 ms |
| Python Graphiti, run 2 | 5,577,590 / 306,234 | 444 / 428 | 384 ms |
| graphiti-net, in memory | 5,835,616 / 315,284 | 429 / 422 | 310 ms |
| graphiti-net, PostgreSQL | 5,894,065 / 330,101 | 438 / 441 | 318 ms |

Search time includes embedding the query with OpenAI, which is most of it.

**Reading it.** graphiti-net answers at least as well as Python Graphiti on this sample: 21 of 24 on both drivers,
against 18 and 19 for two upstream runs. With 24 questions a difference of two or three answers is within noise, so
the claim is parity, not superiority. graphiti-net used about 6% more ingestion tokens; its graphs are the same size.
Its searches were faster.

## Caveats

- 24 questions; repeat on more before 1.0.
- Ingestion times are not compared: the runs shared one rate limit and ran at different concurrency.
- A transient provider error (rate limit, 502) fails a whole `add_episode` in both implementations. The harness
  retries a question from scratch in a fresh group; no retry was needed in these runs.
