# Question answering on LongMemEval, 102 questions: graphiti-net against Python Graphiti

Date: 2026-11-14. Upstream: Graphiti v0.31.2 on Neo4j 5.26. graphiti-net: commit `e68a5b9` (the 0.2 code), on
PostgreSQL 16 with pgvector.

## Method

As the [24-question run](2026-11-13-lme-qa.md), with `parity/python/lme_qa.py` and `tools/GraphitiNet.Eval qa`, except:

- **Questions:** 102 from `longmemeval_oracle.json`, 17 for each of the 6 question types, chosen with seed 42 among
  the 51 questions of each type with the fewest messages ([lme-qa-102-questions.json](lme-qa-102-questions.json)).
  1,658 messages per run.
- **Model for building and answering:** DeepSeek `deepseek-flash` (DeepSeek-V4.1-Flash, default settings) through each
  implementation's `OpenAIGenericClient`, instead of `gpt-5-mini`, to keep the cost down. DeepSeek has no `json_schema`
  output, so both used `json_object` with the guided instruction (`StructuredOutputMode.JsonObjectGuided`; the Python
  harness sends the same text from upstream's client, checked by a test). With upstream's plain `json_object` text the
  model sometimes returned the schema instead of an answer, failing whole questions; with the guided text no question
  needed a retry in either run.
- **Embeddings:** OpenAI `text-embedding-3-small` at 1,024 dimensions, as before.
- **Grading:** upstream's `eval.eval_prompt` with `gpt-5.5` as judge, the same Python grader for both runs. Every
  answering prompt was identical to the one upstream's `qa_prompt` builds from the stored context: 0 mismatches in 204
  answers.
- One run per implementation (the 24-question run had two upstream runs, 18 and 19 of 24, as a control for run-to-run
  noise).

## Results

| Run | Correct | Single-session user | Single-session assistant | Preference | Multi-session | Knowledge update | Temporal |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Python Graphiti (Neo4j) | 83 / 102 (81%) | 14/17 | 16/17 | 15/17 | 12/17 | 12/17 | 14/17 |
| **graphiti-net (PostgreSQL)** | **89 / 102 (87%)** | 14/17 | 16/17 | 15/17 | 14/17 | 14/17 | 16/17 |

| Run | Ingestion input / output tokens | Facts / entities | Median search | Median ingestion per question |
| --- | --- | --- | --- | --- |
| Python Graphiti | 31,307,252 / 7,872,429 | 1,889 / 1,847 | 410 ms | 410 s |
| graphiti-net | 31,671,478 / 7,903,987 | 1,920 / 1,859 | 266 ms | 413 s |

Search time includes embedding the query with OpenAI. Both runs ran at the same time, 6 questions at a time each.
Together they cost $15.78 on DeepSeek.

**Reading it.** graphiti-net answered at least as well as Python Graphiti: 89 against 83 of 102. Per question, 7 were
right only with graphiti-net and 1 only with Python Graphiti; an exact McNemar test on those gives p = 0.07, so this is
parity with a lean towards graphiti-net, not proof that it is better. The gap is in multi-session, knowledge-update and
temporal questions, where both lean on facts' dates. Token use (1% more input) and graph size (2% more facts) are the
same within noise. Searches were faster.

## Caveats

- One run each; run-to-run noise was 1 question in 24 for upstream in the earlier run.
- A different model from the 24-question run, so the scores are not comparable with it.
- Questions are the smaller half of each type (up to 51 per type by message count).
- Graded results: [2026-11-14-lme-qa-102/](2026-11-14-lme-qa-102/).
